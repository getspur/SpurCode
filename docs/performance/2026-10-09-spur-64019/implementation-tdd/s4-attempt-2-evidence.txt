Recovery rules
- Exact owned DDL, source uniqueness metadata, schema cookie, clock integrity,
  journal head and file identity are validated. Tracking gaps/corruption/drift
  cause atomic reinstall, a new generation/history floor, and mandatory reseed.
- Revisions advance within a generation. Loss of the clock starts a new epoch;
  old cursors are incomparable, not silently treated as an empty delta.
- No tombstone/history pruning. One row per ever-seen ID retains each domain's
  latest revision, so a later comment/timestamp cannot erase older relevance.
- A writer that dropped the journal can reject a fresh statement AFTER another
  connection repairs it. The failing statement leaves the source row unchanged.
  On that same writer execute:
  SELECT name FROM sqlite_schema WHERE type='table' AND name='spur_issue_changes'
  Then retry the rejected statement. SELECT 1 / PRAGMA schema_version alone do
  not refresh that stale schema. Reconnecting also works but is not used to hide
  the failure in the final regression. Prepared statements may recover without
  this rejection; the feed cannot refresh another connection's schema cache.
- IGNORE/FAIL may conservatively invalidate captured victims although no source
  change committed. ABORT/ROLLBACK undo capture. No false-negative reuse results.
